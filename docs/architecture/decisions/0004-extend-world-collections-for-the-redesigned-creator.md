# ADR 0004: Extend World collections for the redesigned creator

## Status

Accepted. It partially supersedes
[ADR 0003](0003-accept-operator-uploaded-world-collections.md), which stays in force for everything
this record does not change.

## Context

The redesigned World collections creator lets operators keep a collection as a draft until it is
ready, give figures a rarity and skin variants, choose whether a box shows a figure's face, place
the logo on the box, link the author's page and make plush collections. ADR 0003 refused all of
that: `WorldCollectionCheck` rejected plush collections, author links, alternatives and any logo
that was not the plain automatic fit, and the record JSON accepted no key beyond its first set.

The store and the wire constrain how the record can grow:

- `WorldCollectionRecord` is strict JSON: an unknown key fails the parse, on the server when it
  reads its store and on the client when it receives a sync;
- the store file has `format: 1`, and any other format leaves the store degraded (read-only);
- records travel as opaque bytes in `SyncWorldCollectionsPacket`, so the packet itself does not
  change when a record gains a field;
- the client re-registers a collection only when its record bytes change, so bytes that move on
  upgrade would re-register and resync every collection of every world;
- there is no protocol version between client and server.

Plush blocks are registered at start-up, one per bundled plush id, and the 1.21.4 and later item
definitions for them are generated by a protected build script, so a world cannot add plush blocks
at run time.

## Decision

- **Additive optional keys under store format 1.** The record gains the optional keys `draft`,
  `edited_at`, `author_url`, `logo_layout`, `plush` and `rarity_weights`, and each figure the
  optional keys `rarity`, `variants` and `box_face`. They are validated by
  `WorldCollectionRecord` on both sides, and `toJson` leaves each one out while it holds its
  default, so a record that uses none of them keeps exactly the bytes it had: an upgraded world
  re-registers nothing and resyncs nothing. `WorldCollectionStore.FORMAT` stays 1.
- **Downgrade is not supported.** An older jar fails its strict parse of a metadata file that
  holds one of the new keys. When the `.bak` copy still parses, because the last save was the first
  to use a new key, it treats the newer file as unreadable: it sets it aside as `.corrupt` and runs
  on the backup, so the newest edit must be restored from `.corrupt` by hand, and files only that
  edit named may be collected. Otherwise it serves the store degraded: read-only, collecting no
  files and deleting nothing. Upgrading again reads the store as it was left.
- **Same mod version on both sides.** An older client refuses a sync whose records carry new keys,
  and an older server cannot read the new edits, so client and server must run the same BlockPops
  version. There is no negotiation.
- **Drafts.** A draft is a collection that has never been published. It is stored and registered
  like any other, but the materializer enables none of its figures and the machine screen offers it
  nowhere (`ClientWorldCollections.isOffered`). A record is never both a draft and archived.
- **Only operators see drafts.** The server builds two syncs per revision: operators (level 2,
  the level every edit needs) get every registered record, and every other player gets the same
  without the drafts. A player may fetch only the files its own view names, and a draft's files
  only while it is still an operator. Every operator sees every draft, not only its author's, since
  the store records no authorship. No event announces an operator change, so the server checks each
  player once a second and resyncs one whose status no longer matches the view it was sent; a
  deopped player's client then drops the drafts, and one made operator receives them.
- **Publishing is one-way.** The editor creates a collection as a draft (`CREATE_DRAFT`); the
  `create` command and a datapack import of a new collection still make published ones, and an
  import into a draft keeps it a draft. `PUBLISH`, or
  `/blockpops worldcollections publish`, turns a draft into a published collection once it has at
  least one figure that is not retired (else `EMPTY`), and nothing turns it back: a published
  collection leaves the machines by being archived. A draft cannot be archived or restored
  (`NOT_DRAFT`), because it is in no machine to begin with.
- **Only a draft's figures are deleted.** `REMOVE_FIGURE` deletes a figure outright, and only
  from a draft (else `NOT_DRAFT`): players' boxes may name a published figure, so a published
  figure is only ever retired. The deleted figure's files are left to garbage collection. A box an
  operator unlocked from that figure while testing the draft then shows empty.
- **Figure order** is the record's list order, which `REORDER_FIGURES` replaces with an exact
  permutation of every figure id, retired ones included; anything else is refused.
- **Edits travel in atomic batches.** A `BATCH` carries 1 to 48 edits, none of them a batch, a
  `DUPLICATE`, a `PURGE` or an `IMPORT_PACK`, which each stand alone. The server applies them in
  order to a working copy of the store's state, so an edit sees what the ones before it did (a
  `CREATE_DRAFT` followed by a `SET_COLLECTION` of the new id works). It then checks every changed
  record against that whole working state, budgets included, saves the store once, registers each
  changed collection again and schedules one sync. If any edit or any changed record is refused,
  nothing changes and the answer is the first refusal. A single edit is a batch of one. A collection
  whose record ends a batch unchanged keeps its bytes; every other changed collection goes up one
  revision per batch, not per edit, and its `edited_at` is set to the time of the save. A batch
  costs one edit of the rate limit for every 16 edits it holds, rounded up. The client keeps each
  packet at or below 30,000 bytes, under the 32,767 a client-to-server packet may carry, by
  splitting its edits into several batches, each atomic on its own.
- **Extras have edits of their own.** `SET_COLLECTION_EXTRAS` replaces the author link, logo
  placement, plush flag and rarity weights, and `SET_FIGURE_EXTRAS` a figure's rarity, variants and
  box face, leaving its name, files and size alone. Both go in batches, so a figure whose texture or
  model changes can get variants and a face region that fit it in the same atomic step. A face
  that asks for what the figure's kind shows anyway (a skin figure's face on, a model figure's off)
  is stored as the default, so each look has one form in the record.
- **Duplicating copies names, not files.** `DUPLICATE` copies a collection, with every figure,
  retired ones included, and every extra, into a new draft with its own slug and name at revision
  0. The copy names the same stored files, so nothing is uploaded and no file budget grows; the
  store and the sync grow by one record. It may keep naming a file the source has lost, as the
  source may.
- **Purge from the editor.** This amends ADR 0003, under which only the command purged. `PURGE`
  names the collection twice and purges only an archived collection or a draft; a collection still
  in the machines answers `STILL_LIVE` and must be archived first. It then does exactly what the
  command does: the collection is unregistered, its id is never used again in the world, its files
  are left to garbage collection and its boxes show empty. The command still purges any
  collection.
- **Import from the editor.** This also amends ADR 0003. `IMPORT_PACK` runs the same import as
  `importpack`, so it still reads only the server's own datapacks, by an exact `namespace:path`
  the importer's patterns accept: never a path on the client, a URL or a listing of the packs. A
  collection the import creates is a draft when the operator asks for one, and published
  otherwise, as the command makes it; an existing collection keeps whether it is a draft. Either
  way the import records `edited_at` as an edit does: a new collection gets the time of the
  import, and an existing one only when the import changes it.
- **No new packets, and new costs.** Every new request is an action of
  `WorldCollectionEditPacket`, answered by `WorldCollectionStatusPacket`; records and files still
  travel only as ADR 0003 says. An edit, a duplicate and a purge each cost one edit of the rate
  limit (5 a second, 60 a minute, and a batch one per 16 edits). An import reads and writes up to a
  whole collection on the server thread, so it has its own limit of 2 a minute per operator, which
  a degraded store or a malformed name does not spend. An upload counts against the uploader's
  limits only once the server accepts it: at most 120 uploads and 32 MiB a minute, while a file the
  server already stores, and a refused upload, cost nothing. One upload per player and four per
  server still run at once.
- **New answers are appended.** `WorldContentStatus.Result` travels by ordinal, so `NOT_DRAFT`,
  `EMPTY` and `STILL_LIVE` are added at its end, each with its own message.
- **The author link is display-only.** `author_url` is at most 256 printable ASCII characters
  without spaces, parses as a URI with an `http` or `https` scheme and a host, and carries no user
  info; ASCII alone keeps look-alike letters out of it. The game never fetches it: it is shown under
  the collection's name and handed to the player's browser only through the game's own link
  handling, which asks first unless the player turned the link prompt off in their chat
  settings, and opens nothing while chat links are off. This amends ADR 0003's "no URLs"
  consequence for this one shown link.
- **Logo placement** scales the automatic fit by 50 % to 150 % and moves it by up to 4 model pixels
  each way, stored in tenths of a pixel; it needs a logo.
- **Rarity.** A figure is common unless it says rare, epic or legendary. While every figure is
  common the draw stays uniform; once any figure has another rarity, each one is drawn with its
  rarity's weight, 100, 40, 15 and 5 unless the collection sets its own (1 to 1000 each).
  `FigureDefinition` carries the rarity and the weight; bundled and Custom figures keep weight 1.
- **The draw.** `DrawOdds` picks every machine draw and every `/blockpops getbox`. A pool whose
  figures all weigh the same is drawn exactly as before, with one `nextInt` over its size, so the
  seeded draw of the packaged E2E and every bundled collection behave as they did; any other pool
  is drawn by a cumulative roll over the sum of its weights. A guaranteed token still gives a
  figure the player has not found while one is left, picked **by weight** among those, so a
  legendary stays the rarest find even then. The rules of regular tokens (one every three hours of
  the world's game time, up to three) live in `DrawRules`, where the creator's screens read them.
- **Plush collections are delivered as figure blocks.** A World collection marked `plush` is
  listed in the gacha machine's Plushes tab. It cannot have real plush blocks, which are
  registered at start-up, so a win hands out a figure block that draws the figure's model; a
  holographic win marks that figure block holographic, as a bundled plush would be. A
  registered id lives in only one of the registry's boxed and plush maps, so switching a
  collection between the two never leaves a stale entry. A draw from any other plush collection
  with a figure that has no registered plush block is refused before the token is spent.
- **Drafts can be unlocked, not drawn.** An operator's Unlock gives the figures the record does not
  retire, also for a draft or an archived collection, so an operator can try a draft out in the
  world before publishing it. Draws, `/blockpops getbox` and the machine screen still see none of
  them. Boxes an operator unlocked from a draft that is later deleted for good show empty, as the
  boxes of a purged collection do.
- **Machines hold only offered collections.** The server refuses to set a claw or gacha machine to a
  collection it does not know, to a draft or archived World collection, or to a hidden one, and it
  ignores a machine position whose chunk is not loaded instead of loading it.
- **Variants are texture-only.** A figure has at most 4 variants, and a collection at most 128.
  Each is a name and a texture: a skin for a skin figure, or a texture in the model's proportions
  for a model figure. Model, size, poses and box face come from the figure, because a figure's box
  position is computed from its own model's bounds and would be wrong for another model.
  `WorldCollectionCheck` accepts exactly those alternatives, in order, and nothing more.
- **Box face.** A skin figure may only turn its face on or off; a model figure names the face's
  region in its texture, which must lie inside the texture.
- **Datapacks** may carry every new key in `collection.json`, with variant textures in
  `figures/<id>/variant_<n>.png`, each opened by its exact name.
- **The editor reads many local files at once.** For the bulk add, the client's file picker takes
  several files from the native dialog (tinyfd's multiple selection below 26.3, SDL3's from 26.3)
  or from one drop, and the regular files directly inside a dropped folder. It takes at most 256
  dropped files and folders, looks at no more than 4096 entries of a folder and reads at most 256
  files, one level deep, never through a link inside the folder, and only those whose name ends in
  `.png`, `.geo.json` or `.animation.json`; each is checked against its type's byte cap before it is
  read and then gets the same checks as a single file. Paths still never leave the picker, and
  nothing is sent until the operator adds the figures. The bulk add then saves only those
  figures, in batches of at most 8, each atomic on its own, so the upload can be paused or stopped
  between batches with the earlier ones kept; when the server answers that it is busy, as it does
  once the player's upload or edit limit is used up, the client waits 15 seconds and sends the
  rest, at most 8 times in a row.
- **Local previews.** The editor draws a collection before it is saved. The client materializes
  the draft record as the server would, without the server's check, and registers it in a
  client-only overlay of the collection registry under a reserved id, `creator_preview.<slot>`,
  whose dot keeps it from ever being a World collection id or a slug. The overlay answers only on
  the client thread, so the integrated server of a single player world never sees a preview, and
  no list of collections includes one. Local files are decoded under the same content-addressed
  ids a synced copy gets, so a preview stays right after the upload and the sync replaces it in
  place; a file the editor still shows is kept when a sync stops naming it, and every file only
  the editor used is freed when it closes. The figure and box renderers read a turn and a pose
  from the preview's own stack, and from 1.21.4 a box renderer type of its own,
  `blockpops:creator_box`, reserves room in the GUI for a box turned to any angle. Nothing of a
  preview is sent or stored.
- **"Use my skin" reads only this computer.** The figure inspector can put the player's own skin
  into a skin figure, and it downloads nothing to do so: no texture server or any other origin is
  contacted, so the custom collections' single fixed origin
  ([ADR 0002](0002-load-custom-collections-at-runtime.md)) stays the only one the game fetches mod
  content from. The game already keeps every skin it shows in its skin cache, in its assets folder
  at `skins/<first two>/<name>`, where the name is the SHA-1 of the skin's texture hash, the last
  part of the texture link in the textures property the server listed the player with. The client
  takes that hash from its own player list entry, finds the folder through the game's skin manager,
  and reads the file only when it is a regular file of at most 64 KiB, never through a link. The
  bytes then get exactly the checks of a picked skin (a 64×64 PNG, re-encoded without metadata).
  Without a textures property (offline and development games), without a cached file, or when the
  cached skin fails those checks (an old 64×32 skin), the game's default skin from its own resources
  is used instead and the status line says why. The result is a local file like a picked one:
  previewed at once and uploaded only on Save. The texture's pixels are not read back from the GPU,
  because from 1.21.5 the game keeps none for a downloaded skin.
- **The box template is written to the game folder.** "Download box template" copies two images
  that ship in the mod, a 64×64 template with each face of the box in its own colour and a
  labelled guide, to `blockpops/templates/` in the game folder, replacing earlier copies, and
  asks the system to show that folder. It writes nothing else and opens no save dialog, so no
  path is ever chosen or typed.
- **The creator stays development-only for now.** Every way into it, the machine screen's
  **Creator** button, the Settings **Creator** tab and the client command `/blockpopscreator`,
  asks one check, `SettingsScreen.canOpenCreator()`: a development environment, an operator, and
  World collections synced from the server. The command is registered only in a development
  environment, under a root of its own, because a client command that shares the server's
  `/blockpops` root depends on how each loader passes on arguments it does not know. Packaged E2E
  players run production code and are not operators, so their captures cannot change. The server
  still checks every request, whichever way the creator was opened.
- **Test draws stay on the client.** "Test pull" and "Pull 100 times" on the review page draw with
  `DrawOdds` from a random source of the client's own and show the result stamped as a test. They
  send nothing, spend no token and give nobody a figure.

## Consequences

- Worlds made before this change load unchanged and keep their record bytes; a record that uses a
  new feature grows by only the keys it uses, within the existing 96 KiB record cap.
- A world that uses a new feature cannot be edited by an older BlockPops build until it is
  upgraded again, and mixed client and server versions refuse each other's World collections.
- Every edit that changes a collection records `edited_at`, so the first such edit after an
  upgrade already writes a key that older builds cannot read.
- The editor can save many changes, such as a bulk import of figures or a publish together with
  its last edits, as one atomic step instead of a series of partial saves.
- Players open an operator's link only through the game's link handling and its confirmation
  screen; the link is never fetched by the game or the server.
- World plush collections look like boxed figures once placed, not like bundled plushes.
- Players who are not operators never receive a draft's record or files, so a collection being
  prepared stays private to the operators until it is published, and a box an operator unlocked
  from a draft and placed shows empty to them until then. A file a player fetched as an
  operator and released after being deopped counts as a resend if it is fetched again, so a player
  whose status flips repeatedly may see the fallback look until it reconnects.
- Variant textures count towards every quota and are fetched, kept and collected like any other
  file a record references.
- A collection can now be deleted for good from the editor, but only once it is archived or still
  a draft, and only once the operator types its name and the request names it twice; boxes of a
  purged collection show empty, as before.
- Editor imports are as safe as the command's, and their cost on the server thread is bounded by
  their own rate limit.
- Bulk uploads are bounded by bytes as well as by count, and re-sending files the server already
  has is free, so adding many figures at once mostly waits on the one-at-a-time upload itself.
- "Use my skin" costs no network request and needs no new origin, but it only finds a skin the game
  has already downloaded and cached; otherwise the operator gets the default skin and can drop their
  skin file instead.
- Schema tests for the new keys live in a protected follow-up, because tests are protected paths.
